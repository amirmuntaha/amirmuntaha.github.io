Informasi yang membantu laporan bug

  1. URL halaman dan nama alat yang digunakan.
  2. Langkah singkat untuk mengulang masalah.
  3. Hasil yang muncul dan hasil yang Anda harapkan.
  4. Browser, sistem operasi, serta ukuran layar bila masalah terkait tampilan.
  5. Contoh input yang tidak sensitif. Untuk kalkulator, gunakan angka ilustrasi—bukan data rekening atau dokumen kredit.

Keamanan dan privasi saat menghubungi

GitHub issues biasanya dapat dibaca publik. Jangan menempelkan kata sandi, token API, nomor identitas, alamat rumah, nomor rekening, laporan bank, atau data pribadi pihak lain. Jika laporan mengandung celah keamanan, berikan ringkasan minimal terlebih dahulu melalui kanal profil dan tunggu petunjuk sebelum mempublikasikan detail eksploitasi.

Jenis permintaan yang dapat ditinjau

  • Bug yang dapat diulang.
  • Kesalahan rumus atau penjelasan.
  • Masalah aksesibilitas atau tampilan mobile.
  • Tautan rusak dan informasi yang sudah tidak akurat.
  • Saran fitur yang selaras dengan tujuan proyek.
  • Pertanyaan mengenai kebijakan privasi situs.

Saya tidak menjamin waktu respons, dukungan pribadi, konsultasi keuangan, atau pengembangan fitur tertentu. Namun, laporan yang jelas lebih mudah ditinjau dan diprioritaskan.

Sebelum membuat laporan: periksa apakah masalah serupa sudah ada di daftar issues. Menambahkan detail pada laporan yang sama biasanya lebih membantu daripada membuat duplikat.

What makes a useful bug report

  1. The page URL and tool name.
  2. Short reproduction steps.
  3. The actual and expected result.
  4. Browser, operating system, and screen size for layout issues.
  5. A non-sensitive example input. Use illustrative numbers rather than account or loan-document data.

Security and privacy when contacting

GitHub issues are generally public. Do not post passwords, API tokens, identity numbers, home addresses, bank details, statements, or another person's personal data. For a security concern, share only a minimal summary first and wait for guidance before publishing exploit details.

Requests that can be reviewed

  • Reproducible bugs.
  • Formula or explanation errors.
  • Accessibility or mobile-layout problems.
  • Broken links and outdated information.
  • Feature ideas aligned with the project goal.
  • Questions about this site's privacy policy.

I cannot promise response times, personal support, financial consultation, or implementation of a specific feature. Clear reports are nevertheless easier to review and prioritize.

Before reporting: check whether a similar issue already exists. Adding useful detail to one report is generally better than creating a duplicate.
